# Adaptive Design Engine (ADE) — правила проекта

ADE адаптирует существующие профессиональные макеты (сначала PPTX) под новый контент (сначала DOCX), сохраняя стиль и редактируемость, с автоматическим контролем качества.

## Старт любой сессии
1. Прочитай `docs/PROJECT_STATUS.md` (≤60 строк). Это вся необходимая память для начала.
2. Открывай только файлы, нужные задаче. Большие документы — выборочно (`rg`, `Read` с offset/limit).
3. Решения — в `docs/DECISIONS.md`, исследования — в `docs/research/`. Перед новым исследованием проверь, нет ли его там.

## Текущая фаза
Фаза 0 — исследование целесообразности (`docs/FEASIBILITY_STUDY.md`). **Продуктовую разработку не начинать без решения владельца (GO/REVISE/NO-GO).** Разрешены эксперименты в `experiments/`.

## Команда
Project Lead — основная сессия: ставит задачи, решает, кого звать, принимает результат по доказательствам.
Субагенты в `.claude/agents/`: `researcher`, `architect`, `developer`, `qa`.
- Поток по умолчанию: Lead → (researcher) → architect → developer → qa → Lead. Не зови агента, если его вклад не нужен.
- QA не правит код и не принимает собственные исправления. Дефект возвращается разработчику с шагами воспроизведения.
- Параллельные агенты не редактируют один и тот же файл. Владелец файла указывается в задаче.
- Субагенту передаётся только релевантный контекст: задача, критерии приёмки, пути к нужным файлам — не история диалога.

## Модели
- `opus` — архитектура, критический анализ, приёмка.
- `sonnet` — исследование, реализация по ТЗ, QA.
- `haiku` — механические задачи (переименования, форматирование, сводки логов), если качество не страдает.

## Экономия токенов
- Логи и вывод тестов не копируются в контекст целиком: `| tail -n 40`, сводки.
- Тесты: адресно по затронутым модулям; полный набор — перед PR.
- Итог каждой задачи записывается в файл, а не остаётся только в диалоге.
- Graphify и подобные индексы — не используются до триггера из `docs/DECISIONS.md` (D-004).

## Качество и безопасность
- Нельзя: сокращать/переписывать контент клиента, терять данные, менять стили произвольно, заменять редактируемые объекты картинками.
- Рендер — дополнение к структурной проверке файла, не замена.
- В репозитории только синтетические макеты и данные. Никаких секретов и клиентских материалов.
- Результат не принимается без доказательства: команда, вывод, файл.

## Память
Markdown-файлы в `docs/` совместимы с Obsidian (обычные ссылки, `[[wikilinks]]` допустимы). GitHub — основное хранилище. Временная ФС облачной сессии не считается хранилищем.
