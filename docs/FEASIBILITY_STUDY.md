## 0. Рекомендация: **REVISE**

Не GO и не NO-GO. Делать продукт стоит, но **не в той форме, что в мастер-промпте**.

Что меняю:
1. **Сужаю продукт.** Не «мультиплатформенный AI-агент», а движок структурной адаптации PPTX-макетов с проверкой качества. Google Slides и Figma — не раньше, чем PPTX докажет ценность на реальных макетах. Мультиплатформенность в первой версии — это затраты без покупателя.
2. **Меняю главный риск.** Мастер-промпт считает трудной частью адаптацию (добавить карточку, строку). Эксперимент показал: на чистом макете это решаемо за день (**точно**, spike_01). Трудная часть — **понять чужой макет**: какие фигуры образуют карточку, что является процессом, где ось повторения. Это не проверено ни мной, ни в публичных источниках.
3. **Меняю позиционирование.** Copilot Agent Mode, Claude for PowerPoint и ChatGPT for PowerPoint в 2026 году уже правят деки внутри PowerPoint (**точно**, market.md [3][4][20]). Отдельное приложение «ещё один AI для слайдов» проиграет дистрибуции. Защищаемая ниша — **точная детерминированная адаптация + проверка**, которую эти агенты официально делают плохо (**точно**, Microsoft: «Copilot just isn't built for that kind of precise formatting work yet», market.md [9]). Форма поставки — CLI/библиотека + MCP/Skill, который эти же агенты могут вызывать.
4. **Ставлю два ворота (gates) до MVP**, см. раздел 11. Если ворота не пройдены — NO-GO, потеряно 2–3 недели, а не квартал.

## 1. Есть ли реальная потребность?

**Вероятно, да — для узкого сегмента.**
- ~7 ч/неделю на PowerPoint, 37% — форматирование, 47% презентаций не соответствуют бренду (опрос Empower 2020, 1102 респондента) — **точно** как данные опроса, но опрос вендора и старый.
- Консалтинг: слайды — 40–60% времени аналитика; при изменении контента слайд разбирают и собирают заново (Wharton 2026, ~20 интервью) — **точно**, малая выборка.
- Рыночная цена ручной работы: $13–66 за слайд (24Slides), $800–3000 за дек — **точно**.
- Gamma: запрос «генерировать по лейаутам моего шаблона» — 113 голосов, «our own templates — not themes» — **точно**.

Чего нет: ни одного интервью с потенциальным покупателем ADE. Сегменты ниже — **предположение** до интервью.

## 2. Кто будет пользоваться (гипотезы для проверки)

| Сегмент | Почему | Риск |
|---|---|---|
| Студии и фрилансеры дизайна презентаций | Перенос контента в готовый макет — их себестоимость; они же лучше всех оценят качество | Маленький рынок, чувствительны к цене |
| Аналитики консалтинга и банков | 40–60% времени на слайды, жёсткие корпоративные шаблоны | Закрытые корпоративные среды, Copilot уже куплен |
| Регулярная отчётность по фиксированному макету (ежемесячные/квартальные деки) | Один макет, меняются данные и число строк/категорий — идеальный кейс для детерминированного движка | Конкурирует с генераторами отчётов (Plumsail, Aspose) и think-cell |

**Мой выбор для первого пилота: третий сегмент** (**предположение**). Там макет повторяется, ценность измерима в часах, и именно там генераторы шаблонов ломаются на структурных изменениях.

## 5. Что до сих пор делается руками
Перенос контента в фирменный макет; подгонка композиции под другое число элементов; укладка длинного текста; обновление категорий диаграмм; проверка наложений и выходов за поля; и новое — перестройка шаблонов, чтобы с ними справлялся Copilot (**точно**, market.md §ручной труд).

## 6. Насколько востребована именно *адаптация готовых макетов*
Прямых измерений спроса нет. Косвенно: 113 голосов в Gamma, жалобы на Copilot 2024–2025, существование рынка $13–66/слайд — **вероятно**, спрос есть. Публичных бенчмарков структурной адаптации не найдено ни у кого — **точно** (поиск researcher). Это и риск (не знаем, насколько хорош Copilot), и возможность (бенчмарк сам по себе — маркетинговый актив).

## 7. Что надёжно автоматизируется (доказательства)

Эксперимент `experiments/spike_01` (синтетический макет, python-pptx 1.0.2 + прямой OOXML, рендер LibreOffice). Цикл: developer → qa → developer → qa.

| Операция | Результат | Уверенность |
|---|---|---|
| Таблица 5 → 7 строк, чередование заливки | Работает: клон `a:tr` через одну строку | **точно** (qa PASS ×2) |
| Диаграмма 3 → 4 категории | Работает: `replace_data` обновляет XML-кэш и встроенный xlsx, цвет серии сохранён | **точно** |
| Карточки 3 → 4 | Работает после исправлений: клон группы + перенумерация id + единый кегль заголовков (20→16pt) | **точно** на синтетике |
| Процесс 4 → 5 этапов (фигуры + коннекторы) | Работает после исправлений; ветка уменьшения кругов не покрыта | **точно** на синтетике |
| Длинный текст | Работает: метрики шрифта через Pillow, расчёт 14 строк = 14 в рендере, сноска сдвигается, текст не сокращается | **точно** на синтетике |

Самое ценное в эксперименте — **дефекты**:
1. Первый структурный QA дал PASS, а на рендере слова «Редактируемость» и «Масштабирование» рвались посередине. Значит, одной проверки структуры недостаточно; нужны метрические проверки текста + рендер (**точно**).
2. Независимый QA нашёл дубли `p:cNvPr id` после клонирования — PowerPoint такие файлы может «ремонтировать». Мой собственный QA этого не проверял (**точно**). Это прямой аргумент за отдельного QA-агента.

Чего эксперимент **не** доказал: работу на реальных макетах, совместимость с PowerPoint (только LibreOffice), SmartArt, плейсхолдеры/мастер-слайды.

## 8. Что технически трудно или нестабильно

| Проблема | Почему | Уверенность |
|---|---|---|
| Распознавание структуры чужого макета (что — карточка, что — процесс, ось повторения) | Имена фигур случайны, группировка произвольна, стили наследуются из master/layout | **вероятно** главная трудность; не измерено |
| Укладка текста, совпадающая с PowerPoint | Ни одна платформа не даёт API «измерь текст как я»; `normAutofit fontScale` считает только PowerPoint | **точно** (platforms.md A.1, A.5) |
| Рендер для визуального QA | LibreOffice расходится с PowerPoint; SmartArt показывает старую картинку `drawing.xml` | **точно** |
| SmartArt | python-pptx не поддерживает; Aspose умеет `AddNode` (платный); перерисовка после правки данных не проверена | **точно** / эксперимент нужен |
| Новые серии в диаграмме | python-pptx даёт им цвет последней серии (#539), теряет числовой формат (#666) | **точно** |
| Перенос таблицы на следующий слайд | Нужна логика пагинации и повтор шапки | **вероятно** решаемо, не проверено |
| Google Slides | Нет нативных диаграмм (только из Sheets), autofit read-only, 60 записей/мин | **точно** |
| Figma | Нет нативных диаграмм, таблиц в Design; запись только через Plugin API/MCP, MCP-запись станет платной | **точно** |

## 9. Что станет конкурентным преимуществом

1. **Структурная адаптация чужого макета нативными объектами** — никто публично не подтверждает (**точно** по результатам поиска; **предположение**, что никто этого не умеет внутри).
2. **Проверяемое качество**: детерминированный QA (контент 1:1, наложения, разрывы слов, id, редактируемость) + отчёт к каждому файлу. Агенты-генераторы такого не дают.
3. **Опубликованный бенчмарк** «один макет → Copilot / Claude / ChatGPT / ADE».
4. **Встраиваемость**: ADE как MCP-инструмент для тех же агентов — не воюет с их дистрибуцией, а использует её.

Не преимущество: «мультиплатформенность» (никто не платит за неё в первой версии), «AI-дизайн» (это делают все).

## 10. Минимальный продукт и уровни

**MVP** (одна платформа, детерминированное ядро, LLM только для сопоставления контента):
- Вход: PPTX-макет + DOCX/Markdown-контент. Выход: PPTX + PDF + QA-отчёт.
- Распознавание: таблицы, нативные диаграммы, повторяющиеся группы (карточки), плейсхолдеры; ручная разметка ролей как запасной путь, если автодетект не уверен.
- Операции: замена текста/чисел; строки таблицы ±N с пагинацией; категории диаграммы ±N; карточки ±1–2 в ряду; текст — расчёт размера с ограничением кегля (не ниже 75%) и сдвигом соседей.
- QA: структурные + метрические проверки + рендер; отказ с объяснением вместо «тихо плохо».
- Сопоставление контента: LLM предлагает маппинг «блок документа → слот макета», детерминированный код применяет. Контент не переписывается.

**Advanced:**
- Процессы/таймлайны 4 → 5 на фигурах и коннекторах; перестройка сетки (4 карточки → 2×2).
- SmartArt (через Aspose или прямой `dgm`-XML) — после эксперимента.
- Подбор подходящего слайда из библиотеки макетов под блок контента.
- Google Slides-адаптер.

**Experimental:**
- Figma / Figma Slides через Plugin API или MCP (auto-layout отлично подходит для карточек, но нет диаграмм).
- Автодетект ролей vision-моделью по рендеру.
- Перенос макета между платформами (не рекомендую: импорт PPTX в Slides/Figma превращает диаграммы в картинки, **точно**).

## 11. Ворота перед MVP (что сделать в ближайшие 2–3 недели)

**Gate A — реальные макеты.** Собрать 15–20 профессиональных PPTX-макетов из открытых источников с разрешённой лицензией (без клиентских данных). Измерить: доля слайдов, где автоматически верно найдены повторяющиеся группы, таблицы, диаграммы. Порог (**предположение**, обсуждаемо): ≥70% слайдов без ручной разметки и ≥90% с ручной.
**Gate B — сравнение с агентами.** Одни и те же 5 задач (3→4 карточки, 5→7 строк, 3→4 категории, длинный текст, 4→5 этапов) через Copilot Agent Mode, Claude for PowerPoint, ChatGPT for PowerPoint. Если они уже делают это приемлемо — продукт превращается в QA-слой или NO-GO. Нужна помощь Анны: у меня нет доступа к PowerPoint и этим подпискам.

## 13. Архитектура под несколько редакторов

Гипотеза мастер-промпта (Input Adapters → Analysis → IDM → Mapping → Layout → Output Adapters → QA) **верна по направлению, избыточна по объёму для MVP**.

Что оставить:
- **Семантическая модель макета (IDM-lite)** вместо полной универсальной модели дизайна: `Slot` (текст с политикой переполнения), `Repeater` (ось, шаблон элемента, min/max, правила перераспределения), `Table`, `Chart` (данные, не геометрия), `Fixed` (не трогать). Она описывает *что можно менять*, а не всё, что нарисовано. Объекты хранятся ссылками на нативные элементы адаптера, а не копией геометрии.
- **Матрица возможностей адаптера**: операция → нативно / эмулируется / не поддерживается. Различия платформ (**точно**, platforms.md): в PPTX диаграмма = XML + встроенный xlsx; в Slides = связанная Google Sheet; в Figma диаграмм нет; таблиц в Figma Design нет; auto-layout есть только в Figma.
- **Общий модуль измерения текста** с фирменными шрифтами — нужен на всех платформах, ни одна его не даёт.
- **Детерминированный solver раскладки** + LLM только для сопоставления контента. Причина: воспроизводимость, тестируемость, стоимость.

Что не строить сейчас: Input Adapters для разных форматов контента (DOCX/Markdown хватит), универсальную геометрическую модель, Output Adapters кроме PPTX.

Правило против жёсткой связи с PowerPoint: ядро (`ade/core`) не импортирует `pptx`/`lxml`; адаптер реализует интерфейс `detect() → IDM`, `apply(plan) → file`, `capabilities()`. Проверяется линтером импортов.

Детальная архитектура — `docs/ARCHITECTURE.md` после решения по этому документу.

## 14. Как обеспечить профессиональный визуальный результат
1. Не создавать новый дизайн: только клонировать существующие элементы и менять их геометрию в пределах правил.
2. Ограничения стиля как жёсткие правила: кегль не ниже 75% исходного и одинаков у однотипных элементов; отступы/зазоры сохраняются; цвета и шрифты только из макета.
3. Трёхслойный QA: структура (id, нативность, xlsx) → метрики (наложения, переполнение, разрыв слов, контент 1:1) → рендер (сравнение с исходным слайдом).
4. Честный отказ: если адаптация нарушает правила — пометить слайд для человека, а не выдать плохой результат.

## 15. Как управлять разработкой командой агентов

Проверено в этой сессии (**точно**):
- Конфиги `.claude/agents/{researcher,architect,developer,qa}.md` работают как реальные субагенты: вызваны по имени, developer исправил дефекты, qa независимо перепроверил. Нюанс: агенты, созданные посреди сессии, доступны со следующего хода (D-002).
- Параллельно работали три исследователя по непересекающимся темам; каждый писал в свой файл.
- Независимый QA нашёл дефект (дубли id), который пропустил автор кода.

Правила (в `CLAUDE.md`): Lead решает состав; QA не правит код; у каждого файла один владелец; субагенту — только задача, критерии приёмки и пути к файлам.

Выводы:

- Узкое задание с готовым контекстом снижает расход в разы: QA раунд 2 — 18k против 80k у раунда 1 (**точно** для этой пары; одна пара — не статистика).
